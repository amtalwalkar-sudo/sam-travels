## Implemented foundation (not yet full conformance)

- `packages/application/src/shared-form-runtime.ts` defines versioned form definitions, declared field validation, working-copy lifecycle, explicit Save versus Submit, revision-conflict protection, and stable operation identity.
- `packages/application/src/form-submission-port.ts` carries form ID/version, operation ID, action and values across the application boundary.
- `packages/application/src/record-form-working-copy-repository.ts` stores recoverable copies through the authoritative atomic record repository. This makes the same envelope usable by the browser IndexedDB and Android Room record adapters and the existing generic-record backup participant.
- The working-copy repository and runtime now expose definition-scoped discovery of in-progress drafts, so a presentation can offer a real resume path after a reload rather than requiring the original in-memory instance ID. Completed and unrelated forms are excluded from the resumable-draft list.
- Tests cover validation, explicit zero values, strict dates, restored working copies, definition-scoped draft discovery, Save/Submit distinction, stale revisions, and record-backed storage.
- Business Setup, Vehicle, Driver, and Compliance are the migrated Admin UI consumers. Business Setup uses `admin.business-setup` v1; Vehicle uses `admin.vehicle` v1; Driver uses `admin.driver` v1; Compliance uses `admin.compliance` v1. All use the shared runtime and record-backed working-copy repository, and dispatch writes through their existing application-owned services. Vehicle and Driver edit commands carry the working-copy instance identity and record revision captured when editing began. Compliance creation retains immutable renewal linkage and delegates validation and persistence to ComplianceService. Driver assignment history and Work selection remain owned by their existing services. Loan details uses `admin.loan-details` v1 through the shared runtime, with create/edit, durable draft resume, revision-aware updates and dispatch through `FinanceLoanService`; historical loan dates remain valid. Loan payment, prepayment and settlement now use `admin.loan-payment`, `admin.loan-prepayment` and `admin.loan-settlement` v1 through the shared runtime and record-backed drafts. Their presentation delegates to `FinanceLoanPaymentService`, `FinanceLoanPrepaymentService` and `FinanceLoanSettlementService`. The Android overlay renders and submits cancellation-fee and completed-ride Fare/Toll/Parking forms through Room-backed shared working-copy envelopes.

## Maintenance Expense correction pilot — acceptance status

- The Admin Maintenance presentation exposes correction/history for eligible general-expense records and constructs the shared `HistoricalCorrectionService` against the platform's atomic record repository. Browser PWA resolves to IndexedDB; installed Android resolves to the Room-backed `RoomRecordRepository` through `RoomStorePlugin`.
- The feature policy allows only the `amountPaise` field for this pilot and validates the projected expense. The service derives the correction actor from the authenticated identity service, checks Driver self-correction versus PIN-verified Admin authority, preserves the original record, appends a reasoned correction, and atomically advances the correction-chain head with revision checks.
- PWA application-service tests cover Driver self-correction, denial when a different Driver attempts the correction, Admin correction of another actor's record, append-only history, actor/reason/before/after/supersedes provenance, replay with the same correction ID, correction-ID payload-reuse rejection, and stale-chain rejection.
- Android instrumentation covers atomic Room persistence of correction + chain-head batches, stale-head rejection without a partial commit, and native backup/restore recovery of original expense, correction history and final chain head.
- The correction form now retains the same operation ID after an ambiguous submission failure; changing the amount or reason starts a new operation identity. This makes an ordinary retry replay-safe rather than silently issuing a fresh correction ID.
- Android instrumentation now drives the rendered Admin Maintenance correction form in the installed Capacitor WebView: it enrolls a PIN-protected Admin, activates the Admin role, submits a correction through the live platform repository, and asserts the original expense remains unchanged while exactly one correction and the matching chain head are persisted in Room. This is covered in `MaintenanceCorrectionCapacitorAcceptanceTest` and CI run #1925.
- **Still not accepted end to end across the full matrix:** PWA browser UI submission is not browser-driven; Driver-own versus other-Driver denial remains verified at the PWA application-service layer rather than through live Android UI; and replay/recovery of the exact correction submitted by the live WebView test is not yet asserted in that same test. Separate Android Room tests prove correction-batch atomicity, stale-head rejection, and backup/restore of correction history. Do not mark the complete cross-platform correction pilot as accepted until those surface-level cases are connected and pass.
- Native overlay-originated Work/Trip attribution is a separate workflow path and is not evidence for Maintenance correction attribution.

## Existing aligned boundaries

- Admin forms submit through owning application capability services rather than writing directly to Room, IndexedDB, or feature tables.
- Admin service dependencies are supplied explicitly from the single application composition root.
- Feature-owned application services remain authoritative for business validation and durable writes.

### Recovery evidence already exercised by automation

A pending GPS intent survives actual app/test process death, startup recovery preserves the active shift, completion records the event/outbox, and replay does not append a duplicate. This proves the enqueue → process-death → recovery → completion path; it does not simulate death at every CPU instruction or inside a Room transaction.
- Android Room and browser IndexedDB tests inject completion-write failures at the event, state, intent and outbox boundaries. Each failed completion leaves the authoritative state unchanged, keeps the intent pending and writes no outbox entry. - Restore automation covers replacement-transaction rollback and a pre-restore checkpoint/journal that survives Room reopen and recovers authoritative records after an interrupted replacement. Backup/restore tests also cover pending Work/Trip financial obligations and their working copies.
