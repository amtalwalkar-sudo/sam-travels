# Shared Form Conformance Audit

**Status:** Partial — shared mechanics and record-backed working-copy adapter implemented; Maintenance and all current Loan web forms migrated and CI-verified; Work/Trip cancellation-fee and completed-ride Fare/Toll/Parking slices implemented on PWA and Android overlay with shared-runtime drafts, idempotent submission and CI-verified recovery tests; broader recovery acceptance remains open  
**Authority:** `FORM_ARCHITECTURE_AND_BEHAVIOUR_CONTRACT.md`  
**Scope audited:** Current Admin web forms, Work/Trip workflow, application-service boundary and Android overlay  
**Explicit exclusions:** Performance remains a product placeholder. Physical-device form acceptance is deferred.

## Implemented foundation (not yet full conformance)

- `packages/application/src/shared-form-runtime.ts` defines versioned form definitions, declared field validation, working-copy lifecycle, explicit Save versus Submit, revision-conflict protection, and stable operation identity.
- `packages/application/src/form-submission-port.ts` carries form ID/version, operation ID, action and values across the application boundary.
- `packages/application/src/record-form-working-copy-repository.ts` stores recoverable copies through the authoritative atomic record repository. This makes the same envelope usable by the browser IndexedDB and Android Room record adapters and the existing generic-record backup participant.
- The working-copy repository and runtime now expose definition-scoped discovery of in-progress drafts, so a presentation can offer a real resume path after a reload rather than requiring the original in-memory instance ID. Completed and unrelated forms are excluded from the resumable-draft list.
- Tests cover validation, explicit zero values, strict dates, restored working copies, definition-scoped draft discovery, Save/Submit distinction, stale revisions, and record-backed storage.
- Business Setup, Vehicle, Driver, and Compliance are the migrated Admin UI consumers. Business Setup uses `admin.business-setup` v1; Vehicle uses `admin.vehicle` v1; Driver uses `admin.driver` v1; Compliance uses `admin.compliance` v1. All use the shared runtime and record-backed working-copy repository, and dispatch writes through their existing application-owned services. Vehicle and Driver edit commands carry the working-copy instance identity and record revision captured when editing began. Compliance creation retains immutable renewal linkage and delegates validation and persistence to ComplianceService. Driver assignment history and Work selection remain owned by their existing services. Loan details uses `admin.loan-details` v1 through the shared runtime, with create/edit, durable draft resume, revision-aware updates and dispatch through `FinanceLoanService`; historical loan dates remain valid. Loan payment, prepayment and settlement now use `admin.loan-payment`, `admin.loan-prepayment` and `admin.loan-settlement` v1 through the shared runtime and record-backed drafts. Their presentation delegates to `FinanceLoanPaymentService`, `FinanceLoanPrepaymentService` and `FinanceLoanSettlementService`. The Android overlay renders and submits cancellation-fee and completed-ride Fare/Toll/Parking forms through Room-backed shared working-copy envelopes.

## Existing aligned boundaries

- Admin forms submit through owning application capability services rather than writing directly to Room, IndexedDB, or feature tables.
- Admin service dependencies are supplied explicitly from the single application composition root.
- Feature-owned application services remain authoritative for business validation and durable writes.

Work/Trip financial parity is partial. The mandatory cancellation-fee slice is implemented in the PWA Work screen and Android overlay:
- `work.trip-cancellation-fee` v1 is a canonical shared-runtime definition. Missing fee is rejected; an explicitly entered ₹0 is valid. Amounts are stored as integer paise.
- Cancellation creates the trip-linked `work:trip-financial-obligation:<tripId>` record in the same browser IndexedDB or Android Room transaction as the cancellation event. The obligation stores the cancellation event identity and remains pending until submitted.
- PWA uses `SharedFormRuntime`, `RecordFormWorkingCopyRepository` and `TripFinancialService`. Android overlay uses `DriverCancellationFeePanel` and `DriverCancellationFeeStore`, writing the same `__sam_travels_form_working_copy__:work.trip-cancellation-fee:<tripId>` envelope and stable operation identity.
- Both surfaces retain recoverable drafts, reject negative or fractional-paise values, submit idempotently, and block another Work action/shift-end while the fee obligation is pending. Shift-end is guarded at queue and commit boundaries.
- Cancelled trips have no Toll or Parking fields or entries. The cancellation fee is not merged into Fare.
- Recovery coverage added after the initial cancellation-fee slice: the browser backup/restore test exports and restores the pending obligation plus its in-progress zero-valued working copy; the Android backup snapshot test verifies the same records survive export/restore; and a persistent Room database close/reopen test verifies the pending obligation and draft survive process-style database reopening. These tests do not claim physical-device acceptance or prove every OS process-death/force-stop scenario.
