# Persistence and Schema Contract

**Status:** Stage 2 implementation contract and compatibility reference.
**Principle:** Persisted source records are versioned contracts. A reader must never guess a future format or silently discard data to make an unsupported format appear readable.

## Independent version domains

These versions are intentionally separate; do not conflate them.

| Contract | Current version | Authority |
|---|---:|---|
| Record envelope | 1 | `packages/core/src/persistence-contract.ts` |
| Browser IndexedDB/Dexie database | 5 | `packages/storage-browser/src/database.ts` |
| Android Room database | 3 | `android/app/src/main/java/in/samtravels/app/LocalDatabase.kt` |
| Backup snapshot and manifest | 1 | Core and native backup snapshot contracts |
| Backup participant payload | 1 per participant | Browser participant registry / Room participant annotations and adapters |

A record-envelope version describes the JSON record contract. Dexie and Room versions describe physical database layouts and migration history. Snapshot and participant versions describe backup serialization. Changing one does not implicitly change another.

## Record envelope v1

Every ordinary platform-owned persisted record uses this envelope:

| Field | Requirement |
|---|---|
| `id` | Required, non-empty, trimmed stable identity |
| `schemaVersion` | Required integer, exactly 1 until an explicit record migration exists |
| `createdAt`, `updatedAt` | Required ISO-8601 instants with timezone; updatedAt must not precede createdAt |
| `source` | Required enum: `web`, `android`, `import`, `integration` |
| `revision` | Required positive safe integer |
| `data` | Required payload; its feature contract owns its shape |
| `businessDate` | Optional valid calendar date in `YYYY-MM-DD` |
| `deletedAt` | Optional null or ISO-8601 instant |

Validation occurs in the application service and browser/Android persistence write adapters. Backup export and restore validate platform-owned record envelopes too. Reads of legacy Room rows retain their original payload so migration and recovery tooling can inspect historical data; typed application-service reads validate before returning a record to business logic.

Unknown record schema versions are rejected. Do not coerce, strip fields, or fall back to a guessed version. A future record version needs an explicit deterministic migration before it becomes the current version.

## Work command, intent, state, event and outbox contracts

Work persistence is not a generic record envelope: it uses its own explicit v1 discriminants in `packages/domain/src/driver-workflow.ts` and the native mirror `DriverWorkflowContract.kt`.

- Commands: schema version 1; non-empty command/event/idempotency identities; event type from the five supported shift/trip/cancel discriminants; origin surface `pwa` or `native_overlay`; valid prior-state enum; non-negative safe revision; timezone-qualified transition instant.
- Intents: command plus status enum (`pending_location`, `needs_attention`, `recorded`, `rejected`), valid created/updated instants, monotonic update time, and optional string reason.
- State projections: schema version 1, non-negative revision, known workflow state, and valid optional transition timestamps/event identity.
- Committed events: event identity must match the command, revision must equal expected revision + 1, commit timestamp must be valid, and GPS evidence must satisfy coordinate, accuracy and transition-window constraints.
- Outbox rows: stable revision-derived identity, supported integration/event/payload contract versions, boolean delivery state, and valid creation instant.

Browser and native storage validate these discriminants at enqueue/commit, persisted reads, backup export and restore. Malformed persisted state is surfaced as a contract failure rather than silently skipped.

## Physical database migrations

### Browser IndexedDB / Dexie

Current database version: **5**. The ordered upgrade history is retained in `packages/storage-browser/src/database.ts`:

- v1: authoritative `records` table.
- v2: driver state, intents, events, and outbox tables.
- v3: recovery checkpoint table.
- v4: encrypted credential vault tables.
- v5: bounded diagnostics table.

Dexie upgrades are additive and ordered. Historical v1 databases must open through the complete v1→v5 chain. Never delete or recreate an existing database as a migration fallback.

### Android Room

Current database version: **3**. Migrations are explicit and ordered in `LocalDatabase`:

- 1→2: add the `records.updatedAt` index.
- 2→3: create the Log Book events table and index, copy legacy `driver-event:` rows, then remove those legacy rows within the Room migration transaction.

Every Room database builder must register both migrations. Unknown future Room versions fail closed; destructive migration fallback is not permitted. Room schema JSON snapshots are generated by KSP and retained under `android/app/schemas`.

## Backup snapshot v1 and participant contracts

The top-level snapshot and manifest each declare schema version 1. Participant identity, feature owner, snapshot version, adapter, and restore-validator identity are explicit. Browser and native participant registries must agree with the actual tables/entities.

- Browser participants: platform records, Work driver state/intents/outbox, and Log Book events.
- Native participants: platform records, Work driver records, and Log Book events.
- Recovery checkpoints, credentials, and diagnostics are not business snapshot participants; their exclusion is explicit in the adapter/table coverage contract.

Restore validates snapshot version, participant inventory, record counts, stable identities, participant ownership, and platform record envelopes before checkpoint/replacement. Unsupported future snapshot or participant versions are rejected before mutation. Legacy participant-less native snapshots may use the existing explicit legacy normalizer; this is not permission to accept unknown future versions.

## Historical and adversarial fixtures

Fixtures are maintained under `fixtures/persistence/`:

- `record-envelope-v1-valid.json`: supported historical record envelope.
- `record-envelope-v1-missing-data.json`: malformed partial record.
- `record-envelope-v2-future.json`: unsupported future record version.
- `backup-v1-duplicate-identities.json`: duplicate stable identity.
- `backup-v2-future-manifest.json`: unsupported future backup version.
- `room-v1.sql` and `room-v2.sql`: historical Room database layouts and source rows.

Tests must prove successful historical migration, payload preservation, repeatable opening, validation rejection, duplicate-identity rejection, future-version safety, and rollback on injected migration failure. Keep a fixture when a format is retired; do not rewrite historical fixtures to resemble the current schema.

## Change protocol

1. Add a historical fixture for the old format.
2. Define the new schema/record/participant version and deterministic migration.
3. Validate at every write and restore ingress.
4. Test migration success, repeatability, failure rollback, malformed inputs, duplicate identities, and unsupported future versions.
5. Update this contract and the Stage 2 acceptance evidence only after the full architecture, web, and Android CI gates pass.
